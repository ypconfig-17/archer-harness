# 上下文策略：我们希望得到什么效果

这份说明用于讨论三种内置策略的实际取舍。参数以当前实现为准；“预期”表示设计方向，不能当作已经测出的质量、速度或成本结论。

## 1. 先说结论

我们希望长任务继续推进时，模型能看见最近的工作细节，并通过旧历史的交接摘要接上之前的调查和判断，同时避免每一轮都重复读取越来越多的内容。

三种策略做的是不同取舍：

| 策略 | 主要意图 | 预期表现 | 要付出的代价 |
| --- | --- | --- | --- |
| 上下文质量优先 | 给最近的工作保留更多原文，并投入较多摘要预算 | 长任务中的近期细节更容易直接查到，旧调查有交接可接续 | 摘要本身有消耗，保留原文较多；不保证回答一定更准确 |
| 均衡模式 | 让原文多保留一段时间，再按需整理 | 短任务较少受到整理打断，长任务在达到阈值后交接 | 整理前的输入可能更长，不能承诺总成本居中 |
| Token 优化优先 | 较早整理，减少之后反复携带的原文 | 长会话后续请求有机会变小 | 更依赖摘要，可能遗漏细节或需要重新读取证据；不保证总费用最低 |

短会话没有触发整理时，三种策略往往没有可见差别。差异主要出现在长调查、多轮工具调用和连续修改任务中。

## 2. 什么是“整理上下文”

可以把一次长任务理解为持续增长的工作笔记。模型每次继续工作，需要重新收到本轮允许它看到的材料。

这里有两种整理动作，作用不同。

### 历史摘要：把旧工作整理成交接笔记

例如，前面读了几个模块、排除了两个原因、确认了一个问题，后面还要继续改代码。摘要希望留下发现、假设、失败方案、判断前提、下一步及证据来源，减少旧助手回复和工具输出反复占用输入。

近期受保护的原文继续保留；用户和系统消息也保留原文。原始历史仍在记录中，摘要没有删除它。

这会额外调用一次模型，所以整理当下有成本和等待。收益要看后面还能继续多少轮，以及摘要是否保留了继续工作所需的信息。

### 工具结果节选：临时缩短过大的工具正文

例如，一次工具输出很长，导致整份请求已经装不下。系统可以保留正文的一部分，并告诉模型如何通过历史读取工具取回完整输出。

节选只在已经超出输入额度时尝试，而且必须能够从已提交记录可靠读回原文。它不替我们理解文件，也不保证被省略的部分无关紧要。

三种内置策略的步骤顺序都是“工具节选 → 历史摘要”。不过窗口尚未超限时，节选不会执行，系统仍然可以直接进入摘要判断。

## 3. 三种配置具体差在哪里

Token 是衡量文本体积的单位，不能直接当作字数或消息条数。以下数字均以 token 为单位，运行时使用本地估算。

| 配置项 | 质量优先 | 均衡 | Token 优化优先 |
| --- | ---: | ---: | ---: |
| 未被摘要覆盖的历史，超过多少时尝试整理 | 60,000 | 100,000 | 40,000 |
| 接近窗口上限时，希望提前留出的余量 | 24,000 | 16,384 | 32,000 |
| 摘要后近期原文的保留目标 | 40,000 | 20,000 | 12,000 |
| 单次摘要输出预算 | 16,384 | 自动，最多 16,384 | 8,192 |
| 摘要使用的推理等级 | 高 | 跟随任务 | 低 |
| 工具节选至少要节省整份输入的比例 | 20% | 25% | 15% |

这些数字需要结合下面的解释理解。

**触发摘要有两条线，任意一条达到就可以尝试。** 一条看未被摘要覆盖的历史积累了多少；另一条看完整请求距离可用输入上限还有多远。完整请求还包含规则、工具声明、项目参考等材料，所以不能只看对话正文。

**“保留近期原文”是目标，不是固定截取量。** 系统按完整的工具调用与结果选择边界，不能为了凑数字把一组调用拆开。找不到合适分段时，可以不摘要。增长统计也可能包含无法被摘要替换的用户消息，因此达到阈值不代表一定能省下空间。

**摘要预算是上限，不是摘要长度承诺。** 思考和正文共用预算，还受模型输出能力及窗口比例限制；摘要正文另有大小和结构校验。高推理等级表示更多思考投入的配置意图，不能据此推断质量一定更高。模型不支持明确指定的等级时会报错，不会自动换成另一个等级。

**节选比例是采用门槛。** 例如整份输入原来估算 100,000，质量优先要求至少节省 20,000 才采用节选。门槛更低表示愿意接受较小的空间收益，不表示每次节选都会删掉更多正文。单条工具正文的保留额度独立受输入额度 25% 和剩余窗口限制。

## 4. 用同一个场景比较

假设某次请求可用于输入的额度是 200,000。这个额度已经扣除了模型输出预留和安全余量，不能直接用模型宣传的总窗口代替。

此时三种策略的“接近满载”触发线分别是：

| 策略 | 完整输入超过此值时尝试摘要 | 近期原文目标 |
| --- | ---: | ---: |
| 质量优先 | 176,000 | 40,000 |
| 均衡 | 183,616 | 20,000 |
| Token 优化优先 | 168,000 | 12,000 |

再假设同一份原始材料中，完整输入为 130,000，未被摘要覆盖的历史为 70,000：

- 质量优先会因历史超过 60,000 而尝试摘要，目标是继续保留较多近期原文。
- 均衡没有达到历史 100,000 或容量触发线，可以继续使用当前原文。
- Token 优化优先会因历史超过 40,000 而尝试摘要，目标是保留较小的近期原文范围。

这是把同一份材料分别交给三种策略判断。实际运行一段时间后，它们采用摘要的时机不同，历史覆盖范围也会不同，不能把这些数字当作三条会一直同步推进的时间线。

还有一个容易忽略的情况：**小窗口可能让三种策略趋同。**

如果可用输入只有 80,000，容量余量最多只能占 15%，即 12,000，所以三种策略的容量触发线都变成 68,000。近期原文目标最多占输入额度的 25%，所以质量优先与均衡都会收敛到 20,000，Token 优化优先仍是 12,000。增长阈值和摘要配置仍有区别。

因此，“质量优先总是保留两倍原文”“三种策略一定在不同时间触发”都不成立。

## 5. 按任务类型，我们期待什么

### 短问题、小改动

没有触发整理时，三种策略都保留当前原文，不会仅因为选择了“质量优先”就多调用模型生成摘要。普通答复的推理等级也不会被摘要配置改变。

### 连续排查、跨文件修改

质量优先的设计意图是给近期工作留下更大的原文范围，让刚读到的代码、刚出现的错误和刚作出的修改更容易被直接看到。旧工作用交接摘要接续。

我们希望它减少丢失近期细节后重复调查的情况，但这需要真实任务验证。摘要也可能遗漏前提，额外整理还有等待与消耗。

### 持续读取大量材料的长会话

Token 优化优先希望更早把旧历史换成交接摘要，降低之后多轮请求重复携带的文本量。

它更依赖摘要和按需重读。若模型频繁找回被省略的内容，节省的输入可能被摘要调用、重读工具和额外轮次抵消。

### 日常任务混合使用

均衡是当前默认的工程起点：让历史积累得更多一些，再根据增长或窗口压力整理。它适合用作比较另外两种策略的基线。

这不表示它已经被证明在准确率、耗时和成本上取得最好的折中。

### 单次输出特别大，或者用户原文特别长

先看工具输出能否可靠节选，再看有没有可以摘要的旧交互。即使选了 Token 优化优先，也可能无法把请求装进窗口。

用户原文、固定规则和必要协议开销不会被悄悄缩短；不可拆的调用批次也不会强行拆开。最终装不下时明确停止。

## 6. 配置什么时候生效，失败后会怎样

在 Web 保存配置后，之后发送或排队的新任务带上该份配置快照；已接受的任务、正在执行的任务和原请求重试继续使用各自已固定的配置。改设置不会改写这些任务。

CLI／SDK 没有给任务指定策略时，沿用创建会话时记录的完整默认配置。重启根据事实恢复，不重新读取代码中的默认模板替换原选择。

整理过程中：

- 某一步没有可处理的分段，或摘要无效、没有收益，会继续尝试后面的步骤。
- 如果最终输入可以容纳，就继续普通推理；否则明确失败。
- 摘要请求和普通推理共用任务预算。没有采用的摘要，已经消耗的用量也不会消失。
- 每个 INFER 最多提交四次摘要请求，重启不会恢复这四次额度；这不是整项任务只能摘要四次。
- 提交确认异常、预算拒绝和计量口径变化会中止流程，不会假装整理成功继续执行。

高级条件只是在这些动作上增加限制。例如，“历史消息数大于某值，并且输入占比超过某值”表示两者都满足后，才继续检查步骤自身的触发线。配置条件本身不会额外触发整理，也不会关闭最终的窗口检查。

## 7. 现在能确认什么，还需要验证什么

目前有行为测试确认：步骤回退、窗口拒绝、收益门槛、调用配对、配置校验、预算记账，以及配置和摘要的恢复规则。测试覆盖这些工程边界，不等于完成了真实模型质量评测。

当前还不能承诺：

- 质量优先一定提高正确率。
- Token 优化优先一定降低总费用或缩短耗时。
- 摘要完全保留所有业务细节。
- 换一种策略就能装下任意长输入。

可以用同一批长任务做后续对比，尽量固定模型、输入、初始材料、工具结果和授权条件，再分别运行三种策略。至少记录下面这些结果：

| 要观察的结果 | 它能回答什么 |
| --- | --- |
| 任务是否完成，结果是否正确，是否违反明确要求 | 策略有没有损害实际工作 |
| 是否重复调查、遗漏关键前提或重复操作 | 摘要是否保留了继续工作需要的信息 |
| 摘要次数、采用次数与重读历史次数 | 整理是否带来收益，还是增加往返 |
| 普通推理、摘要、重读和缓存相关用量 | 总消耗是否真的下降，而不只看某次输入变短 |
| 总耗时与整理时等待 | 用户实际体验是否改善 |
| 估算输入和服务端报告输入的差异 | 当前阈值在实际材料上是否可靠 |

讨论时最值得先确定的是：我们更不能接受“丢失细节、重复工作”，还是更希望降低长会话消耗；愿意为交接摘要等待多久；用哪批真实任务判断效果。参数应围绕这些目标评估，策略名称不能代替结果。
