# 声明式上下文策略链

## 背景

上下文整理需要同时表达参数、执行顺序和触发条件。用户应能通过设置页调整已有步骤的优先级、组合和适用状态；新增整理动作仍由 Handler 的代码与契约明确实现。声明式 Profile 让配置调整与可信执行职责各自保持清晰。

同时，策略语义必须保持可追溯：任务执行时到底用了哪个配置、命中了哪一步、优化前后的估算，都需要从已提交事实读出，不能靠页面当前配置推测。

## 决策

把上下文整理表达为声明式 Profile，由 Handler 按顺序求值；页面只编辑和展示配置。

- Profile 包含 1–8 个有序步骤，每步声明 `kind`、稳定 `id`、`enabled`、可选 `when` 条件和自己的参数。当前步骤类型为历史摘要（`compact`）和工具结果节选（`trim-tool-results`）。
- `when` 是递归 ANY/ALL 条件，读取本地估算指标：`inputRatio`、`estimatedInputTokens`、`uncoveredTokens`、`historyMessages`。条件只做过滤，不自行触发整理；步骤自身的容量线、增长线或超窗线才是触发依据。
- Handler 每次取链中第一个启用、条件成立且触发线命中的步骤执行。没有可摘要分段、摘要无效或无收益、节选未达到收益门槛时，只阻塞当前输入上的该步骤，继续尝试后续步骤；采用任何整理结果后清空阻塞集合并重新评估。每个 INFER 最多提交 4 次摘要请求、每次执行最多 16 轮评估；失败、未确认及未采用请求都占用摘要额度，额度由事实恢复，重启不重置。摘要达到上限后仍允许采用已确认响应和后续节选。提交异常、预算拒绝或计量口径变化立即中止，不能作为步骤回退吞掉。
- 内置三个只读模板（质量优先、均衡、Token 优化优先）作为起始配置。界面修改内置模板时自动创建自定义副本；自定义 Profile 每次保存递增 `revision`。
- Web 在任务提交时解析并深拷贝 Profile 到 `inference.contextProfile`。CLI／SDK 省略任务策略时继承创建会话时写入 `agent.created.inference.contextProfile` 的完整默认快照，显式会话策略优先于内置均衡模板。首个 INFER 固定实际快照，后续 INFER 复用；执行时缺少快照明确拒绝，不根据当前代码补默认值。用户原始任务提交仍用于 requestId 判等，继承默认值不改写幂等签名。
- 实际命中的快照与步骤写入普通推理结果同一提交的 `contextPlan`：`profileId`、`profileName`、`profileRevision`、`beforeTokens`、`afterTokens`、`inputLimit` 和步骤列表（步骤 `id`、`kind`、`reason`、前后估算）。界面只读已提交记录。

## 编排与收益语义

`inference-pipeline.ts` 只组织预算准入、参考准备、上下文整理和真实模型请求的统一记账。`context-management.ts` 是 Handler 的内部固定流程，组织上下文投影、策略选择、摘要复用与收益核验；`context-policy.ts` 只提供纯条件判断和步骤选择，`compaction.ts` 负责摘要分段与输出校验。该拆分保护所有真实模型请求先提交再执行、共享预算和提交异常原样传播的性质，不增加注册器或可执行步骤接口。

节选收益以整理前完整请求的估算输入为分母：`(beforeTokens - afterTokens) / beforeTokens >= minSavingsRatio`。多条工具结果可以共同达到门槛；最终不足门槛时整批保留原文，不泄漏部分改写。单条工具正文的保留额度为 min(4096, floor(输入额度 × 25%)) 个估算 token，还受剩余窗口约束，收益参数不同时控制保留额度。超窗时未必存在同时满足收益和证据边界的整理方案，最终窗口准入仍可明确拒绝。

摘要响应校验失败或没有收益时，用量和响应事实照常保留，后续步骤没有获得额外预算。若后续步骤不能解除超窗，保留具体摘要失败原因；若最终原文或节选输入可以容纳，则继续普通推理并再次检查预算。

## 为什么不是可执行插件

Profile 是数据，不是代码。步骤类型由 Handler 实现，配置不能注入函数、加载工作区代码或改变执行管线。这样做的原因是：整理动作会替换模型可见历史并消耗真实推理预算，允许配置携带实现就等于把可信执行边界交给持久化数据。新增步骤类型仍然是 Handler 的契约变更，需要说明对事实、执行和恢复的影响。

## 安全 Guard 与校验

以下约束不进入 Profile，也不能被页面关闭：

- 窗口准入：最终请求超过输入额度时拒绝执行。
- 摘要校验：空摘要、截断、包含工具计划、交接证据无效或没有减少完整输入时不采用。
- 完整批次：摘要只替换完整的旧助手/工具交互，用户原文和近期受保护原文保留。
- 可追溯性：采用版本、步骤和优化前后估算随结果提交。

配置结构和语义约束统一放在 `ContextProfileSchema`，页面保存、HTTP／SDK 输入及事实解析都执行同一校验：参数范围、步骤标识唯一、最多启用一个节选步骤、条件嵌套不超过 4 层、单个步骤不超过 24 个比较。条件深度在结构解析阶段受限，不先递归解析任意深度再做事后检查。参数超出窗口比例（预留不超过输入额度 15%、近期目标不超过 25%）属于运行时约束，由 Handler 计算时收敛，不悄悄改写保存的配置。

## 影响与边界

- 配置仅使用 `ContextProfile`。HTTP／SDK 或执行事实中的非法配置明确拒绝；浏览器偏好引用未知模板时回退默认选择，不为已提交事实补造策略。
- 页面与后端共用 `@archer/contracts` 的 Schema，配置结构只有一份定义。
- 可追溯性依赖新增的 `contextPlan` 结果字段；它记录已发生的整理，不改变原始历史、摘要采用流程或用量账本。
- 阈值仍是待质量评测的工程基线。Profile 让调整成本降低，不证明任何参数组合能提高任务成功率。

## 验证方法

- `tests/contracts/context-profile.test.ts` 验证 API 与事实所用 Schema 一致拒绝重复 ID、多重节选、超深条件和过多比较。
- `tests/handler/context-window.test.ts` 验证无分段、无效摘要、无收益摘要及摘要上限之后的步骤回退、恢复不重置摘要额度、预算继续准入和缺失策略拒绝。
- `tests/handler/tool-result-window.test.ts` 验证节选来源、调用配对与完整输入收益门槛。
- `tests/archer/model-settings.test.ts` 验证 HTTP／SDK 拒绝非法配置且不提交输入，默认快照随创建事实、多轮、排队和重启保留，原提交重试仍幂等。
- 全量验证使用 `pnpm test`、`pnpm typecheck` 和 `pnpm lint`。

工具结果节选采用 85% 容量线与 4096 个估算 token 的单条保留上限，避免接近窗口时反复传输大结果。仍需满足 Profile 条件和完整输入收益门槛；不会自动启用关闭的步骤。仅改变当次模型请求投影，Journal 原文、摘要覆盖与恢复事实不变。验证命令：`pnpm exec vitest run tests/handler/context-policy.test.ts tests/handler/tool-result-window.test.ts tests/handler/context-window.test.ts`，覆盖提前节选、低占用原文、来源与配对、收益及超窗拒绝。
