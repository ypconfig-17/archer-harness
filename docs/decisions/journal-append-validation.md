# JSONL Journal 追加校验与缓存边界

## 保护的性质

Journal 保留每个 Agent 一个 `agents/<agentId>.jsonl` 文件，每行是一个完整事件数组批次。事件信封包含 Agent 序号、Turn 子序号、时间戳与事实。只有以换行结束的完整批次参与恢复；完整行必须经过 JSON、AgentEventSchema、Agent 身份、事件 ID、连续 Agent/Turn 序号及非倒退时间戳校验。缺失文件代表空日志，不代表被外部删除的历史能够自动恢复。

`expectedSeq` 必须等于已验证日志的最后 Agent 序号。新草稿的信封由 Journal 赋值，新事件也必须通过恢复协议校验。文件同步和父目录同步都必须确认，才能报告提交成功。可能已经开始修改文件后的任何异常都作为 `COMMIT_UNKNOWN` 隔离，不重试、不推测写入未发生。

进程内串行锁不能覆盖另一个 Journal 实例或进程；文件属性不能证明历史字节未被改写。因此追加同时使用明确的提交互斥和内容验证，不能仅依赖大小、inode 或 mtime 命中缓存。

## 每次追加的边界

1. 同实例按 Agent 串行化；独占创建 `<agentId>.jsonl.lock`，取得协作进程之间的提交权。已有锁返回 `CONFLICT`，不触碰日志。
2. 使用同一 `a+` 文件句柄读取文件一次，检查读取前后的版本及实际读取长度。文件属性变化或读取不一致立即拒绝。
3. 已有缓存时，核对设备、inode、确认长度，并对完整已确认前缀重新计算 SHA-256。前缀摘要不匹配、文件替换或截断使当前实例隔离；不会清空缓存后悄悄接受被改写的历史。
4. 只对缓存长度之后的完整新批次执行 JSON 与协议校验，以缓存中的 Agent/Turn 序号和时间戳为基线。新增完整批次的行号按原文件位置报告。首次追加没有缓存，需要完整验证历史。
5. 比较 `expectedSeq`，为新增事实和本批草稿建立 Turn 序号覆盖层。确认前不修改缓存 Map。新草稿非法时，在任何截断或追加之前拒绝。
6. 重新检查路径版本及锁的文件身份。只有完整历史已验证，才允许截去未完成末行；随后追加一行批次、同步文件和父目录，并检查最终路径、句柄身份及文件长度。
7. 文件关闭、锁关闭与解除均成功后，才发布新的摘要、字节长度、行数、Agent/Turn 序号和时间戳缓存。

缓存不保存正文，不是持久化 checkpoint，也不是第二份事实源。缓存空间随 Agent 和 Turn 数量增长，不随正文体积增长；正常追加只更新受影响 Turn 的序号，不复制全部 Turn Map。失败或未知提交不能推进确认状态。`CONFLICT` 和写入前的参数错误可以保留旧缓存，因为下一次使用前仍会读取并核对完整前缀；检测到历史损坏或变更后，当前实例拒绝继续追加。

## 内容校验与复杂度取舍

恢复读取始终解析并校验所有完整批次，即使调用方提供 `afterSeq`，也必须在完整验证后再过滤结果。恢复读取不使用追加缓存，不修复文件，也不解除隔离。

正常追加中可以复用的是：已验证历史的 JSON 解析结果所对应的序号基线，以及同一份读取内容中已经确定的末行边界。完整恢复、第一次追加和新的外部完整批次仍需要逐条协议校验。文件已确认前缀的内容验证不能只用 stat 替代。

此设计每次仍读取一次全部日志并计算前缀摘要，读取和摘要成本仍为 O(日志字节数)。它减少重复全量读取及已确认历史的 JSON/Schema 校验，不承诺固定尾部读取或 O(1) 追加。若需要在任意外部改写可发生的条件下仅读尾部，又要检测历史中的任意字节变化，现有普通文件 API 无法同时满足要求。进一步消除全量读取，需要更强的独占写入约束或明确的存储协议变更，不能静默改成只信任元数据。

SHA-256 依赖其抗碰撞性质，仅验证已读字节与已确认前缀的一致性，不是签名、不可篡改证明或外部副作用证明。

## 多进程与外部修改

提交锁依赖本地文件系统对独占创建、文件身份和路径的正常一致性语义。所有写入者都必须使用同一锁协议，持锁者之外不得删除或替换锁。此互斥只保护一次 Journal 提交，不提供跨 Archer 的 Agent 调度、租约、心跳或分布式执行。不要让旧的、不遵守协议的写入者与当前写入者同时工作；网络文件系统不在已验证范围内。

进程之间顺序追加允许发生：已确认前缀相同且新增批次有效时，当前实例验证增量，再比较实际序号与 expectedSeq。并发持锁冲突不会自动等待或重试。

离线外部改写、截断、替换可在内容和身份检查中发现；读取或写入期间观察到的版本、身份或长度变化同样拒绝。任意不协作的进程可以在最后一次检查之后继续写入、替换或删除路径，普通文件 API 与协作锁无法原子阻止这种竞态。因此**不承诺与任意非协作外部写入同时操作的原子性或完整检测**。外部编辑、备份恢复、截断和文件替换必须先停止全部写入者。文件系统修改时间不是代码签名或文件身份的永久证明。

## 异常退出与遗留锁

锁中只有诊断用 PID，不是租约，也不表示该批已提交。不能通过时间过期或 PID 存活检查自动抢占：暂停、PID 复用和检查之后的竞争都不能证明安全。

写入开始后的错误会保留锁并冻结当前实例，包括部分写入、文件/目录同步确认丢失、文件关闭、路径变化或解锁失败。异常退出也可能留下锁。完整读取可以用于检查实际存在的批次，但不能仅凭完整行判断某个外部操作是否执行过。

遗留锁需要显式运维处理：停止所有共享该目录的写入者；保留日志和锁以供核查；完整校验日志并判断未知执行是否需要对账；确认没有持有者后仅移除对应锁；使用新的 Journal / Archer 实例完成恢复。损坏的完整历史不得靠删除数据或截断成较短日志来解锁。校验失败时保持隔离。

锁解除未单独增加第三次目录同步，正常提交仍包含文件与目录两次同步。因此即使一次提交已成功返回，随后的系统崩溃也可能使锁删除的目录变更未持久化、恢复时再次看到遗留锁；这只允许导致人工确认，不能自动抢占。该设计明确选择保守的恢复可用性，不宣称任意崩溃后都能无人工干预恢复追加。

服务端现有“移出加载范围”入口仅移动 Agent JSONL，不处理提交锁；如该日志存在遗留锁，运维仍须按上述步骤单独核查和处理，不能通过移出日志绕过锁的判断。

## 验证与基准

```bash
pnpm --filter @archer/storage... build
pnpm exec vitest run tests/storage/agent-journal.test.ts tests/archer
```

测试覆盖正常增量、只读一次历史、Turn 序号、CAS 冲突、跨实例顺序追加、真实子进程争用和异常退出、完整恢复校验、同尺寸改写并恢复 mtime、截断、替换、读取及写入期间变化、部分尾行、多字节边界、锁替换、同步/关闭/解锁确认失败和未知提交隔离。完整批次损坏时，修复末行不能改变原文件。

性能脚本只在临时目录写入生成日志，不接触应用数据：

```bash
node scripts/benchmark-journal.mjs --baseline /absolute/path/to/baseline-agent-journal.ts --samples 40 --output /tmp/archer-journal-benchmark.json
```

baseline 是调用方明确提供的外部 TypeScript 快照；脚本转译到临时目录，结束后清理，不在产品代码中保留旧实现或兼容路径。运行前先构建当前 storage 及其依赖。

三个起始规模为 100、1,000、10,000 条事件，每条包含 1,024 字符正文，两种实现使用相同初始字节和相同追加负载。每种规模连续追加 40 次，因此实际历史从 N 增至 N+40；首次冷缓存追加包含在 p50/p95 和累计耗时中，并单列首次数据。另做抛弃式预热，不刷新操作系统页缓存；文件同步与目录同步均计入延迟。测量进程 CPU 时间，不把它当作桌面整体 CPU。

读取字节统计是文件 API 返回的 Journal 数据字节，不是物理磁盘流量，不包括 stat 等元数据系统调用。报告保留每次追加的读取字节和延迟、p50/p95、累计耗时、进程 CPU 时间、环境和两份源码摘要。计时包含系统调度、文件系统及 fsync 的波动，单机单轮数据不能推导所有环境的固定提升倍率。

原始测量数据见 [Journal append 基准](../benchmarks/journal-append.json)。Renderer 进度订阅、历史投影、滚动和布局并未随这项存储优化一同修改，仍按 [桌面性能边界与采样](../guides/desktop-performance.md) 独立定位。

桌面启动器让 Electron 使用独立进程组，将 SIGINT / SIGTERM 转换为 IPC 退出请求；主进程转入 app.quit，统一经过 before-quit 等待后端停止。父进程 IPC 断开同样请求正常退出。
信号处理不解除 Journal 锁，也不把未知提交转换为成功；强制终止、系统崩溃和后端停止超时仍可能需要上述离线核查。
