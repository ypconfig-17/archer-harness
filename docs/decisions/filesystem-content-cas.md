# 文件内容 revision 与受控 CAS 边界

## 背景

mtime、大小和实例内计数不能可靠标识文件内容：同大小外部更新可以保留时间，实例计数又无法跨实例与重新打开比较。Agent 内部串行也无法阻止其他 Agent 或另一 provider 实例同时通过同一个文件版本检查。仅按文件路径、工作目录或 provider 对象加锁还会遗漏重复实例、重叠根与文件别名。

## 决策

文件 revision 使用原始字节的 SHA-256 内容摘要。正文与读取 revision 来自同一次字节读取；stat 与条件写入检查使用相同算法，不保存必须恢复的实例计数。revision 表示内容状态，相同字节共享 revision；同内容写入和内容恢复原值不表示新的内容版本。

在 Node.js 文件 provider 的模块实例内，为所有公开文件访问共享一条串行队列。条件检查、写入和结果读取处于同一临界区，受控读取也不与受控写入交错。使用单队列使硬链接等多地址来源无需再引入资源身份注册表，能力仍使用既有来源引用。

## 取舍与保证范围

该边界保证同模块实例中的多个 Agent、provider 与文件别名不能并发消费同一个旧内容版本完成不同内容的更新。它不序列化外部编辑器、宿主 Shell、其他进程、worker 或其他模块副本的写入，不宣称宿主文件系统具备原子条件替换操作。create-only 使用文件系统排他创建；其他写入仍遵守未知副作用及恢复规则。

代价是不同文件也串行，stat 需要读取完整内容。流式摘要限制单次计算的内存占用，无法消除 I/O 成本。摘要不是写入次数、持久化锁或幂等键；它不检测内容恢复原值的 ABA 历史。

## 重新评估条件

如果受控并发度或摘要读取成本成为实际瓶颈，需要在保持同源别名与快照保证的前提下重新评估更细的同步或读取协议。若要求与不受控外部写入之间的强原子 CAS，应提供独占的写入环境或原子条件更新后端，不能通过进程内路径锁或 rename 宣称获得该保证。
